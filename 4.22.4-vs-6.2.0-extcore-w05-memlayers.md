# Multi-layer memory: 4.22.4 vs 6.2.0 (medium extended-core + 5% writes)

Date: 2026-11-23  
Workload: `medium-extended-core-w05-falkor` (10k queries, extended-core, ~5% writes)  
Config: p=8, mps=2000, timeout 20s, clean bulk reload before each engine  
Results: `Results-261123-4.22.4-vs-6.2.0-extcore-w05-memlayers/`  
Summary: `ui/public/summaries/falkordb_4.22.4_vs_6.2.0_extcore_w05_memlayers.json`

## What was added

Falkor runs now capture **four memory layers** (before run, every 2s peak sample, final snapshot into `metrics.prom`):

| Layer | Metric(s) | Source |
|-------|-----------|--------|
| Graph (logical) | `falkordb_graph_memory_usage_mb` + `falkordb_graph_memory_component_mb{component=…}` | `GRAPH.MEMORY USAGE falkor` |
| Redis allocator | `falkordb_redis_used_memory_bytes` | `INFO memory` → `used_memory` |
| Redis RSS | `falkordb_redis_used_memory_rss_bytes` + `…_peak_bytes` | `INFO memory` → `used_memory_rss` |
| Container cgroup | `falkordb_container_memory_usage_bytes` + `…_peak_bytes` | `docker stats` (via `FALKOR_DOCKER_CONTAINER` or host-port match) |
| Host process (legacy) | `falkor_memory_usage` | sysinfo `redis-server` on **host** (unreliable for Docker) |

Code: `src/falkor/falkor_driver.rs` (`collect_memory_layers`, peak sampler), gauges in `src/lib.rs`, wired in `run_falkor` (`src/main.rs`). Aggregator UI RAM prefers container peak → Redis RSS peak → graph MB.

## Discrepancy analysis

1. **Logical graph vs Redis allocator** track each other  
   Graph +~22 MB ≈ Redis `used_memory` +~22 MiB.  
   → `GRAPH.MEMORY` is a reasonable proxy for **engine-reported graph footprint**, and Redis heap agrees on the delta.

2. **Redis RSS is higher than `used_memory` on both** (fragmentation / allocator)  
   Peak RSS: 376 vs 424 MiB. 6.2.0 still higher on this layer.

3. **Docker cgroup is the opposite story**  
   Peak container memory: **4.22.4 662 MiB vs 6.2.0 502 MiB** (−24%).  
   End-of-run cgroup: 511 vs 410 MiB.  
   So **actual container utilization is lower on 6.2.0** in this run, even though graph/Redis-reported sizes are higher.

4. **Host process gauge is not trustworthy for Docker**  
   ~7 GiB on both almost certainly matched a wrong/host-wide process (or mis-scaled). Do **not** use `falkor_memory_usage` for external Docker comparisons.

### Practical takeaway

| Question | Answer from this run |
|----------|----------------------|
| Does 6.2.0 use more **graph-reported** memory? | **Yes** (~103 → 125 MB) |
| Does Redis heap agree? | **Yes** (~+22 MiB) |
| Does Redis RSS peak agree? | **Yes** (~+49 MiB) |
| Does the **container** use more memory? | **No — less** (peak −159 MiB) |

Reporting only `GRAPH.MEMORY` would have concluded “6.2.0 is heavier.” Multi-layer capture shows **logical size up, cgroup utilization down** for 6.2.0 under medium extcore + 5% writes.

Possible reasons for cgroup vs Redis RSS gap: different base Redis (image stack), page cache charged to cgroup, thread/stack overhead, measurement timing, Docker Desktop memory accounting on macOS. Redis RSS is “as Redis sees”; cgroup is “what the container is charged.”
