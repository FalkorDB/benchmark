## Verdict

**edge-c is slightly slower overall than 4.22.1 on medium baseline + 5% writes, mainly on median latency.**

| Signal | Observation |
|--------|-------------|
| Correctness / stability | Both: 10k/10k success, 0 errors, 0 timeouts |
| Avg / throughput / p99 / wall time | Within ~2–4% (edge-c slightly slower) |
| p50 | **~+39% on edge-c** (main gap) |
| p95 | **~9% better** on edge-c |
| Deletes (`detach_delete_user`) | Not worse on edge-c in this sample |
| Other writes | Mixed; a few noisy p50 outliers with small **n** |

**Bottom line:** Against 4.22.1, **edge-c does not show a broad correctness or throughput regression** on this workload. The notable issue is a **higher global p50**, consistent with default reentrant write-lock polling (`WRITE_LOCK_POLL_INTERVAL=5`). Avg/p99/QPS remain close. For a fairer lock-path A/B, re-run edge-c with:

```bash
redis-cli -p 6800 GRAPH.CONFIG SET WRITE_LOCK_POLL_INTERVAL 0
```
